# Our Notes

A JavaScript-only shared notebook built with **Next.js and React**, backed by **JSON files**. No database server or SQL is required.

- **Local development:** `data/notes.json` on your computer.
- **Vercel:** a JSON file in a **private Vercel Blob store**, accessed only by the Next.js backend.
- **Readers:** anyone can read notes through the app. The underlying JSON, password hashes, and sessions are never publicly served.
- **Writers:** separate accounts, approved or revoked by the owner.

## Run locally

Requires Node.js 22.13 or newer.

```sh
npm install
npm run setup:key
npm run dev
```

Open **http://localhost:3000** and choose **Set up our space**. Enter your name, username, password, and the private `SETUP_TOKEN` saved in `.env.local`. That setup key prevents a visitor from claiming ownership. It is only needed for the first owner account; do not share it with invited writers.

The JSON file is created automatically when the app first saves data. No migration command is needed. Data and secrets are excluded from Git. To keep development local even if Blob credentials are present, set `NOTES_FILE=./data/notes.json` in `.env.local`.

## Deploy to Vercel

Vercel's deployed filesystem is read-only; temporary files are not durable shared storage. The app therefore stores its JSON in **private Vercel Blob**, not in the deployment bundle or `/tmp`.

1. Push this project to a Git repository and import it into Vercel using the **Next.js** framework preset. Use `npm run build` as the build command.
2. In the project's **Storage** tab, create/connect a **Blob** store with access set to **Private**. Select the option to add its read/write token environment variable to the project.
3. Set the following server-side environment variables:

   | Variable                | Value                                                                                                       |
   | ----------------------- | ----------------------------------------------------------------------------------------------------------- |
   | `BLOB_READ_WRITE_TOKEN` | The token from your private Blob store                                                                      |
   | `SETUP_TOKEN`           | The random secret generated by `npm run setup:key`, or another random secret of at least 32 characters      |
   | `NOTES_BLOB_PATH`       | Optional; defaults to `our-notes/production/notebook.json`                                                  |
   | `APP_URL`               | Optional canonical origin, such as `https://notes.example.com`; omit to accept each deployment's own origin |

   Never prefix these secrets with `NEXT_PUBLIC_`. Do not set `NOTES_FILE` on Vercel. A connected store's OIDC authentication also works when Vercel supplies both `BLOB_STORE_ID` and `VERCEL_OIDC_TOKEN`.

4. Deploy/redeploy. Open the deployed URL and complete owner setup. The private JSON file is created automatically on the first write.
5. Share that URL with your partner. They choose **Sign in → Request access**. Approve their account in **Our circle**.

Use separate private Blob stores for production and previews when possible. As an additional safeguard, preview deployments default to `our-notes/preview/notebook.json`, rather than the production path. A custom `NOTES_BLOB_PATH` overrides this distinction, so set different paths per environment if you customize it.

The app refuses to run with local file storage on Vercel or without Blob credentials there. It does not silently discard notes into temporary storage. Build does not need credentials and does not write data.

### Bring your local notes to Vercel

Before setting up any accounts in the hosted notebook, put the destination's `BLOB_READ_WRITE_TOKEN` in your local `.env.local`, then run:

```sh
npm run storage:upload
# Or choose another local source file:
npm run storage:upload -- /absolute/path/notebook.json
```

This copies local accounts and notes to the configured **empty** private Blob notebook. It refuses to replace existing hosted accounts or notes, leaves your local file unchanged, and omits sessions and rate-limit counters. Sign in on Vercel using your existing username/password; no new owner setup is needed after a successful import.

Once the token is present locally, the app uses Blob unless `NOTES_FILE` explicitly selects local storage. The upload command always targets Blob regardless of `NOTES_FILE`.

## How two people use it

Both open the same deployed URL on their own computers or phones and sign in with separate accounts. Anyone can read; approved writers can create, edit, pin, and delete any note. The app retains the original author and last editor. Only the owner manages writer access.

Visible tabs check for saved changes every **5 seconds** and refresh on focus or reconnection. Each refresh makes one server request. The server reads the latest JSON directly from Blob origin, bypassing the CDN cache, so old permissions or note versions are not reused.

Saving is explicit, rather than character-by-character co-editing. If both people open version 1 of a note, the first save creates version 2. The second save is rejected and the unsaved draft stays open, with **Copy my text** and **Save as new note** options. Background refresh does not replace an open draft. Save before closing the browser; drafts live in the open tab.

### Why simultaneous saves are safe

- **Local:** a cross-process file lock serializes changes. Writes use a temporary file, flush it to disk, then atomically rename it. Readers see a complete old or new JSON document. A failed change does not replace the file.
- **Vercel:** each read includes an ETag. The server writes with `ifMatch`, so an update only succeeds if no other request changed the JSON. On a conflict, it reloads the latest file, rechecks permissions and note versions, and retries. First-file creation uses `allowOverwrite: false`, preventing competing owner setups from overwriting each other.
- Note edits, writer approvals, sessions, and password changes use the same atomic update process. Revocations and session expiry are rechecked on every retry.
- Invalid or corrupt JSON is reported as an error and never silently replaced with an empty notebook.

This design is intended for a small shared notebook. The JSON document is limited to **4 MiB**; each saved change rewrites the document. Blob reads/writes and origin transfer count toward your Vercel usage. Public read responses expose only note data, not the full stored document.

### Same Wi-Fi without deployment

`npm run dev` listens on all local interfaces. Your partner can open `http://YOUR-COMPUTER-LAN-IP:3000`. On macOS, find that IP under System Settings → Wi-Fi → Details → TCP/IP. Keep your computer awake and the server running. Your partner must use your LAN IP, since `localhost` means their own device. For different locations, use the HTTPS Vercel URL.

## Accounts and backups

Passwords are salted scrypt hashes, never plaintext. Random session tokens are stored hashed. Cookies are HttpOnly, SameSite, and Secure on Vercel; sessions expire after 7 days. Changing your password signs out other devices. Authentication attempt limits are saved in the same JSON and apply across serverless instances.

There is no email-based password recovery, so keep passwords in a password manager.

For a local backup, stop the app and copy `data/notes.json`. Restore it while the app is stopped. For a hosted backup, download the private JSON through your authenticated Vercel dashboard. Treat backups as private: they contain password hashes and session records. Do not put the JSON in `public/`, publish its contents, or commit it to Git.

If you have data from the original Python/SQLite version, run `npm run import:sqlite` before creating new accounts in the target store. The JavaScript importer preserves notes, authors, pins, and password hashes without changing the original `data/notes.sqlite3`. Existing passwords still work. Postgres/PGlite are no longer runtime dependencies; their old data, if any, is left untouched rather than automatically discarded or converted.

## Commands

```sh
npm run dev             # Local development
npm run build           # Production build
npm start               # Run the production build
npm test                # File/Blob adapter, auth, migration, and concurrency tests
npm run test:browser    # Full two-person desktop/mobile browser flow
npm run setup:key       # Generate the private first-owner key
npm run storage:upload  # Copy local JSON to an empty private Blob notebook
npm run import:sqlite   # Optional migration from the original app
```

For browser tests, first run `npx playwright install chromium`. If Chrome is installed, use `PLAYWRIGHT_CHROME=1 npm run test:browser`. Tests use temporary JSON files and a simulated Blob SDK; they do not change your actual notebook or contact a live Blob store.

## Structure

- `app/`: Next.js pages, styles, fonts, and API routes.
- `components/Notebook.js`: notebook UI, editor, reader, account controls, and writer approvals.
- `lib/store.mjs`: local JSON persistence, private Blob conditional updates, schema validation.
- `lib/api.mjs`: accounts, authorization, notes, and rate limits.
- `lib/security.mjs`: hashing, input validation, same-origin protections.
- `scripts/`: setup key, optional import, and local-to-Blob upload tools.
- `tests/`: independent clients, multi-process file writes, simulated cloud races, and browser workflows.
